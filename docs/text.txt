you know how in c++ you have to forward declare a symbol (like a function before you use it) or... are forced to move its definition to before its usage?

a multi-pass based compiler solves this by using multiple passes to collect and register symbols before evaluating symbols. this is fine for most languages. until you hit cyclic imports.

file A needs symbol B from File C. and File C needs symbol D from File A.

now both files need to import the other. a pass based compiler breaks here.

so the solution is...

firstly collect all known symbols, then when evaluating any symbol for instance 

let x = y;

if y has been evaluated already, the good to go. if not mark that

"x depends on y"

so whenever y get evaluated your compiler will then fire up to evaluate x.

back to our cyclic import problem.

File A needs symbol B from File C.

but File C hasn't been loaded yet, so A registers a dependency on Symbol B that it needs. when File C eventually gets loaded, it will check all symbols that were waiting for it and resume their evaluation. 

File C needs symbol D from File A.

at this point File has been loaded so this one is straight forward.

at the end of the day if you still have any waiting symbols, you can report cyclic errors. like

let a = b;
let b = a;

they both depend on each other.

---

ISSUE (found 2026-10-26): the compiler does NOT do the above yet for imports.

coral-semantics/decl.crl binds each `import` statement DURING the declare
walk, at the import's own position in the merged file (declareAll ->
checkDecl -> checkImportDecl -> bindImportSymbols -> scopes.lookup, right
there). the loader merges sibling files depth-first (post-order push), so
a file's decls can land AFTER a file that imports it. an import cycle
(A imports B, B imports A) therefore always has one edge pointing forward
in the merged list, and that edge fails with T0001 "symbol not found in
imported module" even though the symbol is pub and the file is loaded.

concretely: compiling coral-ir merges in DFS order from wallvm.crl ->
stmt.crl -> expr.crl, so expr.crl is pushed before stmt.crl; expr.crl's
`import stmt { wvStmt }` looked up wvStmt before stmt.crl's decls were
declared -> T0001 at expr.crl:16. wallvm.crl's identical import works
because wallvm is pushed last. decl.crl:4 claims "cross-file references
resolve in any order" — imports do not.

the principled fix (this doc's design): declareAll should collect ALL
decls first, then bind imports in a second pass (and defer untyped
constant inference, which can reference imported names, to a third pass).
the loader already loads the full import closure eagerly, so no
waiting-symbol machinery is needed for imports specifically — order is
the only problem. value-level cycles (let a = b / let b = a) still want
the dependency-firing evaluator described above.

WORKAROUND currently in coral-ir/expr.crl: path-only `import stmt;`
(binds no symbols, only the module name — immune to ordering) and
qualified calls `stmt::wvStmt(...)` / `stmt::wvSwitchCore(...)`, which
resolve at body-check time when every file's decls are already declared.
remove this workaround when the sema pass order is fixed.
